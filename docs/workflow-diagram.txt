================================================================================
              ML-OPTIMIZER HYPERAGENT — WORKFLOW DIAGRAM
================================================================================

  THE PLUGIN IS THE HYPERAGENT — self-referential, self-improving.

  1. Optimizes the ML model (the task)
     → Evolutionary archive, lineage, 3 mutation operators, staged eval

  2. Optimizes its own optimization strategy (the meta-task)
     → Hyperagent modifies skill instructions. No hardcoded thresholds.

  3. Gets better with each session
     → Promoted meta-patches persist, claude-mem recalls insights.

  Core principle: Standing on the shoulders of giants.
  Research-implement is first-class. User papers get highest priority.

  Always on. Autonomous. Runs until goal reached or user stops.

================================================================================
                          AGENT ROSTER (10 types)
================================================================================

  All agents have memory: local (persistent at .claude/agent-memory-local/)
  All agents read goal_memory.py summary before acting (Phase 7+)

  6 PERSISTENT agents: resumed via SendMessage (accumulated context)
  4 EPHEMERAL agents:  fresh Agent() spawn each time

  DISPATCH PROTOCOL:
    First dispatch:      Agent(subagent_type=...) → save agentId to agent_registry
    Subsequent dispatch: SendMessage(to: agentId) with CONTEXT FROM OTHER AGENTS
    Fallback:            If SendMessage fails → fresh Agent() → update registry

  INTER-AGENT COMMUNICATION (orchestrator relay):
    analyze → tuning:      correlations, branch scores, recommendation
    analyze → research:    pivot reason, dead-end catalog
    analyze → hyperagent:  recommendation, pivot type, improvement %
    monitor → tuning:      OOM batch sizes, divergence patterns
    research → implement:  proposals with findings path
    experiments → analyze: batch completion counts, best metrics
    hyperagent → tuning:   action, evolve HPs, target branch

    Relay validation: schema_validator.py relay <route> <json> before each SendMessage
    Relay acknowledgment: persistent agents emit RELAY_ACK: <route> in response

    |    Q7:  Divergence metric (default: loss)                    |
    |    Q7a: Divergence polarity (auto-inferred)                  |
    |    Q8:  Optimization type (training vs inference)            |
    |    Q9:  Training budget (time / epochs / default)            |
    |    Q10: Anything else?                                       |
    |    Q11: Dataset location                                     |
    |    Q12: Environment manager                                  |
    |                                                              |
    |  RL polarity validation:                                     |
    |    If metric contains "reward"/"return"/"score"              |
    |    AND lower_is_better = True → WARN and confirm             |

  RELIABILITY LAYER (applies to all phases)
  ==========================================
  Phase gates:    pipeline_state.py gate <from> <to> before each transition

  ==================

    |    "both"      — LLM proposals + web/alphaxiv validation       |
    |                                                                |
    |  Scope levels:                                                 |
    |    "training"      — HPs, schedulers, augmentation (safest)    |

  PHASE 7: EXPERIMENT LOOP (Hyperagent-driven)
  ==============================================
  Phase 7 ↔ Phase 8 in a loop. The hyperagent helps Phase 7 by deciding
  what action to take. Analysis advises, hyperagent decides.

  Loop exit conditions:
    1. Target metric achieved
    2. User manually stops
  Autonomous — never auto-stops on plateaus. Hyperagent tries different
  operators. Analysis advises, hyperagent decides.

  +========================================================================+
  |                                                                        |
  |  PRE-LOOP SETUP                                                        |
  |    - Validate pipeline state, verify baseline integrity                |
  |    - Initialize code archive: hyperagent-init (gen-000 from baseline)  |
  |    - Load meta-patches (if meta-improvement has run previously)        |
  |    - Load implementation manifest, sync behavioral memory              |
  |                                                                        |
  |  ITERATION START                                                       |
  |  +------------------------------------------------------------------+  |
  |  |  7.1  HYPERAGENT DECIDES ACTION                                  |  |
  |  |  Agent: hyperagent (PERSISTENT, resumed via SendMessage)         |  |
  |  |                                                                  |  |
  |  |  Reads: archive stats, analysis insights, operator stats,        |  |
  |  |         dead-end catalog, behavioral memory                      |  |
  |  |                                                                  |  |
  |  |  Chooses ONE action:                                             |  |
  |  |    a. HP tuning      → delegates to tuning-agent                 |  |
  |  |    b. LLM code patch → modifies code directly                    |  |
  |  |    c. ShinkaEvolve   → dispatches evolve skill                   |  |
  |  |    d. Research       → dispatches research + implement agents    |  |
  |  |    e. Meta-improve   → modifies skill instructions (max 3/ses)   |  |
  |  +------------------------------------------------------------------+  |
  |                    |                                                   |
  |       +------------+----------+-----------+-----------+                |
  |       |            |          |           |           |                |
  |    hp_tune    llm_patch  shinka_evolve research  meta_improve          |
  |       |            |          |           |           |                |
  |       v            v          v           v           v                |
  |  +------------------------------------------------------------------+  |
  |  |  7.2  EXECUTE ACTION                                             |  |
  |  |                                                                  |  |
  |  |  hp_tune:                                                        |  |
  |  |    tuning-agent proposes configs → experiment-agents parallel    |  |
  |  |    monitor-agent watches for divergence (concurrent)             |  |
  |  |                                                                  |  |
  |  |  llm_patch / shinka_evolve / research_implement:                 |  |
  |  |    1. hyperagent-select → pick parent from archive               |  |
  |  |       (6 strategies: best, score_child_prop, ucb, ...)           |  |
  |  |       UCB1: value/visits + C×sqrt(ln(N)/visits)                  |  |
  |  |       MCTS backprop: ancestors get visit_count++, value_sum+=    |  |
  |  |    2. hyperagent-generate → create code variant                  |  |
  |  |       (ShinkaEvolve: evolve skill does convert→run→inspect)      |  |
  |  |       File handoff: SHINKA_PROVIDER=claude_code,                 |  |
  |  |         SHINKA_HANDOFF_TIMEOUT=600 (10 min per mutation)         |  |
  |  |         Agent writes .inprogress → deadline resets               |  |
  |  |         shinka_run writes .heartbeat every 5s for liveness       |  |
  |  |    3. hyperagent-eval → staged eval (10% budget, adaptive        |  |
  |  |       threshold). If FAIL → archive as filtered, skip full.      |  |
  |  |    4. If PASS → HP-tune (1-2 iters) + full experiment            |  |
  |  |                                                                  |  |
  |  |  meta_improve:                                                   |  |
  |  |    hyperagent-generate (meta_improvement_mode: true)             |  |
  |  |    → reads skill files + archive + operator stats                |  |
  |  |    → writes patched skills to experiments/meta-patches/          |  |
  |  |    → writes meta-changelog.json (skill, change, reason, impact)  |  |
  |  |    → IMMEDIATELY loads patches into subsequent dispatches        |  |
  |  |    → tuning/analysis/research use improved instructions          |  |
  |  +------------------------------------------------------------------+  |
  |                    |                                                   |
  |                    v                                                   |
  |  +------------------------------------------------------------------+  |
  |  |  7.3  ARCHIVE RESULTS                                            |  |
  |  |  hyperagent-archive → update code-archive.jsonl                  |  |
  |  |    - Track genid, parent, lineage, fitness, mutation operator    |  |
  |  |    - Backpropagate UCB score (normalized) through lineage        |  |
  |  |    - Log to behavioral memory + research agenda                  |  |
  |  |    - Update operator_stats in hyperagent_state                   |  |
  |  +------------------------------------------------------------------+  |
  |                    |                                                   |
  |                    v                                                   |
  |  +------------------------------------------------------------------+  |
  |  |  7.4  ANALYZE                                                    |  |
  |  |  Agent: analysis-agent --> ml-optimizer:analyze skill            |  |
  |  |                                                                  |  |
  |  |  Decision tree:                                                  |  |
  |  |    "continue"        → resume hyperagent for next iteration      |  |
  |  |    "code_evolution"  → resume hyperagent (code mutation next)    |  |
  |  |    "hp_expand" etc   → resume hyperagent (HP tuning next)        |  |
  |  |    "stop"            → hyperagent tries other operators first    |  |
  |  |    "method_stacking" → Phase 8 (merge methods, resolve conflict) |  |
  |  |  If meta_improvement_recommended: true                           |  |
  |  |    → hyperagent may choose meta_improve next iteration           |  |
  |  |                                                                  |  |
  |  |  Analysis ADVISES direction, hyperagent DECIDES specific action. |  |
  |  +------------------------------------------------------------------+  |
  |       |                                                                |
  |       +-- Loop back to 7.1 HYPERAGENT DECIDES                          |
  |                                                                        |
  |  +------------------------------------------------------------------+  |
  |  |  7.5  METHOD STACKING (when analysis recommends)                 |  |
  |  |  Triggered by: pivot_type: "method_stacking"                     |  |
  |  |  (multiple improved methods from different papers/code changes)  |  |
  |  |  Requires: git branch strategy                                   |  |
  |  |                                                                  |  |
  |  |  The hyperagent merges best methods sequentially:                |  |
  |  +------------------------------------------------------------------+  |
  +=============================== END LOOP ================================+

  PHASE 8: METHOD STACKING (Hyperagent Driven, in loop with Phase 7)
  ====================================================================
  MANDATORY: Phase 8 is driven by the hyperagent, same as Phase 7.
  Resume via SendMessage(to: agent_registry["hyperagent"]).
  Do NOT implement stacking logic directly in the orchestrator.

  Phase 7 ↔ Phase 8 loop. Analysis advises stacking, hyperagent decides.
  No fixed method count. After stacking → back to Phase 7 on stacked code.
  Agent: hyperagent drives stacking decisions
  Requires: git branch strategy (skipped for file_backup projects)

    +--------------------------------------------------------------+
    |  1. Rank methods by improvement (descending) using           |
    |     rank_methods_for_stacking() from result_analyzer.py      |
    |                                                              |
    |  2. Initialize: best method branch -> ml-opt/stack-1         |
    |                                                              |
    |  3. For each remaining method (in rank order):               |
    |     a. Create ml-opt/stack-<N> from <stack_base_branch>      |
    |        (may be an evolved branch from prior step)            |
    |     b. Merge next method; conflicts -> implement-agent       |
    |     c. Run experiment                                        |
    |     d. Dispatch analysis agent on stacked result:            |
    |        - Compare stacked gain vs best individual             |
    |        - If interference detected:                           |
    |          1. tuning-agent → evolve HPs                        |
    |          2. implement-agent → evolve (ShinkaEvolve)          |
    |          3. tuning-agent → training HPs for evolved          |
    |          4. experiment-agent → run on evolved code           |
    |          5. re-analyze → loop until improved or stop         |
    |        - Else: proceed to HP-tune                            |
    |     e. HP-tune on (potentially evolved) code                 |
    |     f. If degraded: skip, re-branch from last success        |
    |                                                              |
    |  4. Save stacking state (+ evolved_methods) to               |
    |     pipeline-state.json (resumable)                          |
    +--------------------------------------------------------------+

  Reads: results/exp-*.json, implementation-manifest.json, baseline.json
  Writes: results/exp-*.json (stacked_default_hp / stacked_tuned_hp)
          Git branches: ml-opt/stack-<N>

                    |
      (stacking complete → return to Phase 7 on stacked code)
      (target achieved or user stops → Phase 9)
                    v

  Phase 7 ↔ Phase 8 loop:
    Analysis advises "method_stacking" → Phase 8
    After stacking → back to Phase 7 on stacked code
    Meta-improvement inside Phase 7 (one of 5 actions)
    Loop until goal or user stops

  Step 3: META-PATCH PROMOTION (if meta-improvements were made)
  ==============================================================
  Agent: analysis-agent (meta_patches scope) + orchestrator

    1. analysis-agent evaluates each meta-patch:
       - Did experiments after the patch show improvement?
       - Is the modification generalizable?
    2. Present to user: "Promote N strategy improvements to plugin?"
    3. If approved → commit patched skills to plugin's current branch
       (immediately available next session, no merge needed)
    4. Log to behavioral memory + claude-mem for cross-session recall

================================================================================
                          AGENT ROSTER (10 types)
================================================================================

  All agents have memory: local (persistent at .claude/agent-memory-local/)
  All agents read goal_memory.py summary before acting (Phase 7+)

  6 PERSISTENT agents: resumed via SendMessage (accumulated context)
  4 EPHEMERAL agents:  fresh Agent() spawn each time

  DISPATCH PROTOCOL:
    First dispatch:      Agent(subagent_type=...) → save agentId to agent_registry
    Subsequent dispatch: SendMessage(to: agentId) with CONTEXT FROM OTHER AGENTS
    Fallback:            If SendMessage fails → fresh Agent() → update registry

  INTER-AGENT COMMUNICATION (orchestrator relay):
    analyze → tuning:    correlations, branch scores, recommendation
    analyze → research:  pivot reason, dead-end catalog
    monitor → tuning:    OOM batch sizes, divergence patterns
    research → implement: proposals with findings path
    experiments → analyze: batch completion counts, best metrics

================================================================================
                        PHASE-BY-PHASE PIPELINE
================================================================================


  PHASE 0: DISCOVERY
  ===================
  Mode: Plan Mode (read-only, user Q&A)
  Agent: orchestrator (no subagent dispatch)

  User answers 8+ questions:
    Q1: Model path or description
    Q2: Primary metric (accuracy, loss, PSNR, F1, etc.)
    Q3: Lower is better? (for primary metric)
    Q4: Target value (optional)
    Q5: Training command
    Q6: Eval command (if separate)
    Q7: Divergence metric (default: loss)
    Q7a: Divergence lower_is_better? (default: True)
    Q8: Data paths (train, val)
    Q9: Environment manager (conda/venv/none)
    Q10: Model category (supervised/RL/generative)
    Q11: User papers (optional, for research)

  +-- RL polarity validation -------------------------------------------+
  | If divergence_metric contains "reward"/"return"/"score"             |
  | AND divergence_lower_is_better = True (default):                    |
  |   WARN: "For reward-like metrics, divergence means dropping —       |
  |          confirming lower_is_better=False?"                         |
  +---------------------------------------------------------------------+

  Complex optimization: superpowers:brainstorming (multi-objective scenarios)
  Saves: pipeline-state.json (user_choices), user-choices-backup.json
         optimization-goals.json (goal anchor — via goal_memory.py init-goals)

                    |
                    v

    - python3 gpu_check.py  -->  GPU count, VRAM
    - Detect framework (PyTorch/TF/JAX/sklearn/XGBoost/LightGBM)
    - Determine model_category if not set

    |  Step 4: Validate dataset paths and structure                |

    |  Step 6.1: Dry-run validation (NEW)                          |
    |    timeout 120 <train_command_with_minimal_steps>            |

  ==================
  Agent: baseline-agent --> ml-optimizer:baseline skill

    |  3. Check divergence: python3 detect_divergence.py           |

  PHASE 4: USER CHECKPOINT
  =========================
  Agent: orchestrator (user interaction)

  Presents options to user:
    +--------------------------------------------------------------+
    | 1. Continue to research (web search for techniques)          |
    | 2. Skip research, go directly to HP tuning                   |
    | 3. Adjust baseline config and re-run                         |
    | 4. Stop here                                                 |
    | 5. Generate method proposals (research with source: "both")  |
    +--------------------------------------------------------------+

  Option 5 triggers:
    - Ask user for method_proposal_scope (training/architecture/full)
    - research-agent --> ml-optimizer:research (source: "both")
    - User confirms proposals
    - implement-agent --> ml-optimizer:implement
    - Creates branches/backups for each proposal

                    |
     (option 1 or 5 chosen)
                    v

  PHASE 5: RESEARCH
  ==================
  Agent: research-agent --> ml-optimizer:research skill

    +--------------------------------------------------------------+
    |  Source modes:                                               |
    |    "web"       — WebSearch + alphaxiv MCP (parallel)         |
    |    "knowledge" — Structured ideation (6 lenses: Problem-First,|
    |                  Analogical, What Changed, Constraint,        |
    |                  Inversion, Composition). Diverge→converge→   |
    |                  refine. Confidence cap 7/10.                 |
    |    "both"      — LLM proposals + web/alphaxiv validation     |
    |                                                              |
    |  Scope levels:                                               |
    |    "training"      — HPs, schedulers, augmentation (safest)  |
    |    "architecture"  — model changes, loss functions           |
    |    "full"          — any change including data pipeline      |
    |                                                              |
    |  Fuzzy deduplication (NEW):                                  |
    |    - Normalize: lowercase, strip suffixes                    |
    |    - Substring containment check                             |
    |    - Common abbreviation matching (lr↔learning rate, etc.)   |
    |    - >70% word overlap → treat as duplicate                  |
    |                                                              |
    |  Priority scoring:                                           |
    |    score = (impact × confidence) / (11 - feasibility)        |
    +--------------------------------------------------------------+

  Reads: baseline.json, user_choices, existing findings files, dead-ends.json
  Writes: experiments/reports/research-findings.md
          experiments/reports/research-findings-method-proposals.md (if "both")
          experiments/reports/research-agenda.json (living document)
          experiments/reports/research-agenda.md (companion)

  PHASE 6: IMPLEMENT
  ===================
  Agent: implement-agent --> ml-optimizer:implement skill
  Code analysis: feature-dev:code-explorer (dependency tracing)
  Quality gate: feature-dev:code-reviewer (Step 4e.5, advisory)

    +---------------------------------------------------------------+
    |  Strategy A — Git Branch (default):                           |
    |    Parallel via git worktrees (one Agent per proposal):       |
    |      1. git checkout -b ml-opt/<slug> from base branch        |
    |      2. Apply code changes                                    |
    |      3. Validate syntax (py_compile)                          |
    |      4. Run dry-run test                                      |
    |      5. Record in implementation-manifest.json                |
    |                                                               |
    |  Strategy B — File Backup (non-git fallback):                 |
    |    Restore-before-apply pattern (prevents cross-contamination)|
    |      1. Create baseline backup (_baseline/)                   |
    |      2. For EACH proposal:                                    |
    |         a. Restore ALL files from _baseline/ (clean slate)    |
    |         b. Apply this proposal's changes                      |
    |         c. Validate syntax                                    |
    |         d. If pass: backup to backups/<slug>/                 |
    |         e. Restore from _baseline/ (clean for next)           |
    |      3. Experiments run SEQUENTIALLY (not parallel)           |
    +---------------------------------------------------------------+

  Reads: research-findings.md, user-confirmed proposal indices
  Writes: experiments/results/implementation-manifest.json
          Git branches: ml-opt/<slug> (one per proposal)

  PHASE 7: EXPERIMENT LOOP
  =========================
  Loop exit conditions:
    1. Target metric achieved
    2. Analysis agent recommends "stop" 3 consecutive times (triggers stuck protocol)
    3. User manually stops

  +==========================================================================+
  |                                                                          |
  |  ITERATION START                                                         |
  |  +--------------------------------------------------------------------+  |
  |  |  7.1  HP-TUNE                                                      |  |
  |  |  Agent: tuning-agent --> ml-optimizer:hp-tune skill                |  |
  |  |                                                                    |  |
  |  |  Inputs: past results (grouped by code_branch)                     |  |
  |  |  Iter 1: one config per branch + one baseline HP config            |  |
  |  |  Iter 2+: prune underperforming branches, focus configs            |  |
  |  |    - Adaptive branch budget: allocate slots proportionally to      |  |
  |  |      branch scores (improvement_pct × confidence). Score=0 for     |  |
  |  |      branches worse than baseline (no allocation).                 |  |
  |  |    - Checkpoint warm-starting (when enabled): propose configs      |  |
  |  |      that resume from prior checkpoints (lower LR, fewer epochs,   |  |
  |  |      same-branch only). CHECKPOINT_PATH exported in train script.  |  |
  |  |  Batch size: max(num_gpus, 1) proposals                            |  |
  |  |                                                                    |  |
  |  |  WARNING: If branches dropped due to budget, log to                |  |
  |  |  error_tracker with priority order (impact × confidence)           |  |
  |  |                                                                    |  |
  |  |  POST-DISPATCH: goal_memory.py validate-output hp-tune             |  |
  |  |    → Remove configs with frozen params, OOM violations, dead ends  |  |
  |  +--------------------------------------------------------------------+  |
  |                    |                                                     |
  |                    v                                                     |
  |  +--------------------------------------------------------------------+  |
  |  |  7.2  EXPERIMENT                                                   |  |
  |  |  Agent: experiment-agent --> ml-optimizer:experiment skill         |  |
  |  |                                                                    |  |
  |  |  - Capture reproducibility metadata (Step 1.3: seed, pip freeze,   |  |
  |  |    git SHA, framework version)                                     |  |
  |  |  - Generate training scripts per config                            |  |
  |  |  - Run training (parallel across GPUs if available)                |  |
  |  |  - Parse logs, collect metrics                                     |  |
  |  |  - Write exp-NNN.json results (includes "reproducibility" key)     |  |
  |  |  - Timeout: baseline_time × 3 (iter 1), × 2 (iter 2+)              |  |
  |  +--------------------------------------------------------------------+  |
  |                    |                                                     |
  |                    v                                                     |
  |  +--------------------------------------------------------------------+  |
  |  |  7.3  MONITOR (concurrent with experiment)                         |  |
  |  |  Agent: monitor-agent --> ml-optimizer:monitor skill               |  |
  |  |  (skipped for tabular ML: sklearn, XGBoost, LightGBM)              |  |
  |  |                                                                    |  |
  |  |  - Watch divergence_metric (default: "loss")                       |  |
  |  |  - python3 detect_divergence.py '<values>'                         |  |
  |  |  - Returns: healthy | diverged | unmonitored                       |  |
  |  |                                                                    |  |
  |  |  Overfitting detection (if train + val metrics available):         |  |
  |  |  - python3 detect_divergence.py --check-overfitting                |  |
  |  |    '<train_json>' '<val_json>' [--model-category rl|generative]    |  |
  |  |  - Detects val worsening while train improves (patience steps)     |  |
  |  |  - Severity: mild/moderate/severe                                  |  |
  |  |  - Model-category defaults: RL=10, generative=8, supervised=5      |  |
  |  |  - Overfitting = warning (not a kill signal)                       |  |
  |  |                                                                    |  |
  |  |  "unmonitored": metric not found after fallbacks                   |  |
  |  |    → warn user, rely on hard timeout as safety net                 |  |
  |  |  "diverged": kill training, mark experiment as diverged            |  |
  |  |    → validate result: schema_validator.py <exp>.json result        |  |
  |  |                                                                    |  |
  |  |  Recovery mechanisms:                                              |  |
  |  |    - All-diverge recovery: all diverge → retry halved LR           |  |
  |  |    - OOM feedback: record max_batch_size for next hp-tune          |  |
  |  +--------------------------------------------------------------------+  |
  |                    |                                                     |
  |                    v                                                     |
  |  Post-batch validation: schema_validator.py <exp>.json result --strict   |
  |  Enforces completeness (metrics, iteration, method_tier, duration).      |
  |  Incomplete → mark failed, log error.                                    |
  |                    |                                                     |
  |                    v                                                     |
  |  +--------------------------------------------------------------------+  |
  |  |  7.4  ANALYZE + SPECULATIVE HP-TUNE (parallel)                     |  |
  |  |  Agent: analysis-agent --> ml-optimizer:analyze skill              |  |
  |  |                                                                    |  |
  |  |  Runs IN PARALLEL with a speculative hp-tune call:                 |  |
  |  |    - If analyze says "continue" and speculative proposals pass     |  |
  |  |      validation → use them immediately (saves 30-60s idle time)    |  |
  |  |    - If analyze says stop/pivot → discard speculative proposals    |  |
  |  |                                                                    |  |
  |  |  Post-analyze actions:                                             |  |
  |  |    - Statistical confidence: Cohen's d effect sizes, confidence    |  |
  |  |      labeling (high/medium/low), method attribution (Step 2.2)     |  |
  |  |    - HP interaction detection: detect_hp_interactions() finds      |  |
  |  |      2-way HP pairs with synergistic effects on the metric         |  |
  |  |    - Branch scores: compute_branch_scores() for adaptive budget    |  |
  |  |      allocation in next hp-tune iteration                          |  |
  |  |    - goal_memory.py validate-output analyze (metric check)         |  |
  |  |    - goal_memory.py log-behavior method_outcome (per branch)       |  |
  |  |    - Update research agenda (agenda update <idea_id> ...)          |  |
  |  |    - Log dead ends if branches pruned (dead-end add ...)           |  |
  |  |    - Verify baseline integrity (pipeline_state.py verify-baseline) |  |
  |  |    - goal_memory.py sync-from-errors (keep behaviors current)      |  |
  |  |    - Regenerate live dashboard (dashboard.py --live)               |  |
  |  |    - Generate results-table.md (dashboard.py --table)              |  |
  |  |                                                                    |  |
  |  |  Decision tree:                                                    |  |
  |  |    "continue"         → next HP iteration                          |  |
  |  |    "stop"             → check stuck protocol, then Phase 9         |  |
  |  |    "method_proposal"  → trigger 7.5 research pivot                 |  |
  |  |    "qualitative_change" → trigger full research                    |  |
  |  |    "code_refinement" → evolve best branch via ShinkaEvolve         |  |
  |  +--------------------------------------------------------------------+  |
  |                   |                                                      |
  |         +---------+------+----------+-----------+                        |
  |         |         |      |          |           |                        |
  |    "continue"  "stop"  "method_  "qualit.   "code_                       |
  |         |         |    proposal"  change"   refinement"                  |
  |         |         |          |       |          |                        |
  |         |         v          +---+---+          |                        |
  |         |    Phase 9             |              |                        |
  |         |                        v              |                        |
  |  +------+-------------------------------------------------------------+  |
  |  |  7.5  RESEARCH PIVOT / CODE REFINEMENT                             |  |
  |  |                                                                    |  |
  |  |  If method_proposal/qualitative_change:                            |  |
  |  |    research-agent → implement-agent                                |  |
  |  |                                                                    |  |
  |  |  If code_refinement (scope_level=full only):                       |  |
  |  |    1. tuning-agent → propose evolve HPs                            |  |
  |  |    2. implement-agent → Skill("evolve")                            |  |
  |  |       shinka-convert → shinka-run → shinka-inspect → commit        |  |
  |  |    3. tuning-agent → propose training HPs for evolved branch       |  |
  |  |    4. experiment-agent → run training on evolved code              |  |
  |  |    Fallback: shinkaevolve_unavailable → research → implement       |  |
  |  +--------------------------------------------------------------------+  |
  |         |                                                                |
  |         v                                                                |
  |  +--------------------------------------------------------------------+  |
  |  |  7.6  AUTONOMOUS RESEARCH CADENCE                                  |  |
  |  |  (when method_proposal_scope is set)                               |  |
  |  |                                                                    |  |
  |  |  Every hp_batches_per_round batches (default 3):                   |  |
  |  |    Auto-trigger research → implement cycle                         |  |
  |  |    NO user confirmation needed                                     |  |
  |  |    If no new proposals: double cadence (exponential backoff)       |  |
  |  +--------------------------------------------------------------------+  |
  |         |                                                                |
  |         v                                                                |
  |  +--------------------------------------------------------------------+  |
  |  |  7.7  MID-PIPELINE REVIEW (auto-triggered)                         |  |
  |  |  Agent: review-agent --> ml-optimizer:review skill                 |  |
  |  |                                                                    |  |
  |  |  Triggers:                                                         |  |
  |  |    - wasted_budget pattern ≥ 3 occurrences                         |  |
  |  |    - 2 consecutive batches with zero successful experiments        |  |
  |  |                                                                    |  |
  |  |  Output: course correction suggestions in session-review.md        |  |
  |  +--------------------------------------------------------------------+  |
  |         |                                                                |
  |  +--------------------------------------------------------------------+  |
  |  |  7.8  STUCK PROTOCOL                                               |  |
  |  |                                                                    |  |
  |  |  Triggers: 3 consecutive "stop" recommendations                    |  |
  |  |  (one-shot — stuck_protocol_triggered prevents infinite loops)     |  |
  |  |                                                                    |  |
  |  |  1. Read error patterns (error_tracker.py patterns)                |  |
  |  |  2. Read success metrics (error_tracker.py success ...)            |  |
  |  |  3. Read dead-end catalog (error_tracker.py dead-end list)         |  |
  |  |  4. Read research agenda (error_tracker.py agenda list)            |  |
  |  |  5. Dispatch research-agent with full failure context              |  |
  |  |     (constraint: do NOT re-propose dead-end techniques)            |  |
  |  |  6. If new proposals found → implement → reset counter → loop      |  |
  |  |  7. If no proposals → exit loop                                    |  |
  |  +--------------------------------------------------------------------+  |
  |         |                                                                |
  |         +-- Loop back to 7.1 HP-TUNE -->                                 |
  |                                                                          |
  +============================ END LOOP ====================================+

                    |
      (target achieved, 3 consecutive stop recommendations,
       or user manually stops)

  PHASE 8: METHOD STACKING (post-loop, if applicable)
  ====================================================
  Agent: orchestrator dispatches implement-agent + experiment-agent
  Requires: git branch strategy (skipped for file_backup projects)

  Trigger: experiment loop ends AND >= 5 methods improved over baseline

    +--------------------------------------------------------------+
    |  1. Rank methods by improvement (descending) using           |
    |     rank_methods_for_stacking() from result_analyzer.py      |
    |                                                              |
    |  2. Initialize: best method branch -> ml-opt/stack-1         |
    |                                                              |
    |  3. For each remaining method (in rank order):               |
    |     a. Create ml-opt/stack-<N> from <stack_base_branch>      |
    |        (may be an evolved branch from prior step)            |
    |     b. Merge next method; conflicts -> implement-agent       |
    |     c. Run experiment                                        |
    |     d. Dispatch analysis agent on stacked result:            |
    |        - Compare stacked gain vs best individual             |
    |        - If interference detected:                           |
    |          1. tuning-agent → evolve HPs                        |
    |          2. implement-agent → evolve (ShinkaEvolve)          |
    |          3. tuning-agent → training HPs for evolved          |
    |          4. experiment-agent → run on evolved code           |
    |          5. re-analyze → loop until improved or stop         |
    |        - Else: proceed to HP-tune                            |
    |     e. HP-tune on (potentially evolved) code                 |
    |     f. If degraded: skip, re-branch from last success        |
    |                                                              |
    |  4. Save stacking state (+ evolved_methods) to               |
    |     pipeline-state.json (resumable)                          |
    +--------------------------------------------------------------+

  Reads: results/exp-*.json, implementation-manifest.json, baseline.json
  Writes: results/exp-*.json (stacked_default_hp / stacked_tuned_hp)
          Git branches: ml-opt/stack-<N>

                    |
      (stacking complete or skipped)

================================================================================
              ML-OPTIMIZER HYPERAGENT — WORKFLOW DIAGRAM
================================================================================

  THE PLUGIN IS THE HYPERAGENT — self-referential, self-improving.

  1. Optimizes the ML model (the task)
     → Evolutionary archive, lineage, 3 mutation operators, staged eval

  2. Optimizes its own optimization strategy (the meta-task)
     → Hyperagent modifies skill instructions. No hardcoded thresholds.

  3. Gets better with each session
     → Promoted meta-patches persist, claude-mem recalls insights.

  Core principle: Standing on the shoulders of giants.
  Research-implement is first-class. User papers get highest priority.

  Always on. Autonomous. Runs until goal reached or user stops.

================================================================================
                          AGENT ROSTER (10 types)
================================================================================

  All agents have memory: local (persistent at .claude/agent-memory-local/)
  All agents read goal_memory.py summary before acting (Phase 7+)

  6 PERSISTENT agents: resumed via SendMessage (accumulated context)
  4 EPHEMERAL agents:  fresh Agent() spawn each time

  DISPATCH PROTOCOL:
    First dispatch:      Agent(subagent_type=...) → save agentId to agent_registry
    Subsequent dispatch: SendMessage(to: agentId) with CONTEXT FROM OTHER AGENTS
    Fallback:            If SendMessage fails → fresh Agent() → update registry

  INTER-AGENT COMMUNICATION (orchestrator relay):
    analyze → tuning:    correlations, branch scores, recommendation
    analyze → research:  pivot reason, dead-end catalog
    monitor → tuning:    OOM batch sizes, divergence patterns
    research → implement: proposals with findings path
    experiments → analyze: batch completion counts, best metrics

================================================================================
                        PHASE-BY-PHASE PIPELINE
================================================================================


  PHASE 0: DISCOVERY
  ===================
  Mode: Plan Mode (read-only, user Q&A)
  Agent: orchestrator (no subagent dispatch)

  User answers 8+ questions:
    Q1: Model path or description
    Q2: Primary metric (accuracy, loss, PSNR, F1, etc.)
    Q3: Lower is better? (for primary metric)
    Q4: Target value (optional)
    Q5: Training command
    Q6: Eval command (if separate)
    Q7: Divergence metric (default: loss)
    Q7a: Divergence lower_is_better? (default: True)
    Q8: Data paths (train, val)
    Q9: Environment manager (conda/venv/none)
    Q10: Model category (supervised/RL/generative)
    Q11: User papers (optional, for research)

  +-- RL polarity validation -------------------------------------------+
  | If divergence_metric contains "reward"/"return"/"score"             |
  | AND divergence_lower_is_better = True (default):                    |
  |   WARN: "For reward-like metrics, divergence means dropping —       |
  |          confirming lower_is_better=False?"                         |
  +---------------------------------------------------------------------+

  Complex optimization: superpowers:brainstorming (multi-objective scenarios)
  Saves: pipeline-state.json (user_choices), user-choices-backup.json
         optimization-goals.json (goal anchor — via goal_memory.py init-goals)

                    |
                    v

  PHASE 1: UNDERSTAND MODEL
  ==========================
  Agent: orchestrator reads code directly
  External: claude-mem:mem-search (recall past projects)

    - Read model files, config files
    - python3 gpu_check.py  -->  GPU count, VRAM
    - Detect framework (PyTorch/TF/JAX/sklearn/XGBoost/LightGBM)
    - Determine model_category if not set

  Writes: dev_notes.md (session log starts)

  PHASE 4: USER CHECKPOINT
  =========================
  Agent: orchestrator (user interaction)

  Presents options to user:
    +--------------------------------------------------------------+
    | 1. Continue to research (web search for techniques)          |
    | 2. Skip research, go directly to HP tuning                   |
    | 3. Adjust baseline config and re-run                         |
    | 4. Stop here                                                 |
    | 5. Generate method proposals (research with source: "both")  |
    +--------------------------------------------------------------+

  Option 5 triggers:
    - Ask user for method_proposal_scope (training/architecture/full)
    - research-agent --> ml-optimizer:research (source: "both")
    - User confirms proposals
    - implement-agent --> ml-optimizer:implement
    - Creates branches/backups for each proposal

                    |
     (option 1 or 5 chosen)

  PHASE 5: RESEARCH
  ==================
  Agent: research-agent --> ml-optimizer:research skill

    +--------------------------------------------------------------+
    |  Source modes:                                               |
    |    "web"       — WebSearch + alphaxiv MCP (parallel)         |
    |    "knowledge" — Structured ideation (6 lenses: Problem-First,|
    |                  Analogical, What Changed, Constraint,        |
    |                  Inversion, Composition). Diverge→converge→   |
    |                  refine. Confidence cap 7/10.                 |
    |    "both"      — LLM proposals + web/alphaxiv validation     |
    |                                                              |
    |  Scope levels:                                               |
    |    "training"      — HPs, schedulers, augmentation (safest)  |
    |    "architecture"  — model changes, loss functions           |
    |    "full"          — any change including data pipeline      |
    |                                                              |
    |  Fuzzy deduplication (NEW):                                  |
    |    - Normalize: lowercase, strip suffixes                    |
    |    - Substring containment check                             |
    |    - Common abbreviation matching (lr↔learning rate, etc.)   |
    |    - >70% word overlap → treat as duplicate                  |
    |                                                              |
    |  Priority scoring:                                           |
    |    score = (impact × confidence) / (11 - feasibility)        |
    +--------------------------------------------------------------+

  Reads: baseline.json, user_choices, existing findings files, dead-ends.json
  Writes: experiments/reports/research-findings.md
          experiments/reports/research-findings-method-proposals.md (if "both")
          experiments/reports/research-agenda.json (living document)
          experiments/reports/research-agenda.md (companion)

                    v

  PHASE 6: IMPLEMENT
  ===================
  Agent: implement-agent --> ml-optimizer:implement skill
  Code analysis: feature-dev:code-explorer (dependency tracing)
  Quality gate: feature-dev:code-reviewer (Step 4e.5, advisory)

    +---------------------------------------------------------------+
    |  Strategy A — Git Branch (default):                           |
    |    Parallel via git worktrees (one Agent per proposal):       |
    |      1. git checkout -b ml-opt/<slug> from base branch        |
    |      2. Apply code changes                                    |
    |      3. Validate syntax (py_compile)                          |
    |      4. Run dry-run test                                      |
    |      5. Record in implementation-manifest.json                |
    |                                                               |
    |  Strategy B — File Backup (non-git fallback):                 |
    |    Restore-before-apply pattern (prevents cross-contamination)|
    |      1. Create baseline backup (_baseline/)                   |
    |      2. For EACH proposal:                                    |
    |         a. Restore ALL files from _baseline/ (clean slate)    |
    |         b. Apply this proposal's changes                      |
    |         c. Validate syntax                                    |
    |         d. If pass: backup to backups/<slug>/                 |
    |         e. Restore from _baseline/ (clean for next)           |
    |      3. Experiments run SEQUENTIALLY (not parallel)           |
    +---------------------------------------------------------------+

  Reads: research-findings.md, user-confirmed proposal indices
  Writes: experiments/results/implementation-manifest.json
          Git branches: ml-opt/<slug> (one per proposal)

                    v

  PHASE 7: EXPERIMENT LOOP (Hyperagent-driven)
  ==============================================
  Phase 7 ↔ Phase 8 in a loop. The hyperagent helps Phase 7 by deciding
  what action to take. Analysis advises, hyperagent decides.

  Loop exit conditions:
    1. Target metric achieved
    2. User manually stops
  Autonomous — never auto-stops on plateaus. Hyperagent tries different
  operators. Analysis advises, hyperagent decides.

  +==========================================================================+
  |                                                                          |
  |  PRE-LOOP SETUP                                                          |
  |    - Validate pipeline state, verify baseline integrity                  |
  |    - Initialize code archive: hyperagent-init (gen-000 from baseline)    |
  |    - Load meta-patches (if meta-improvement has run previously)          |
  |    - Load implementation manifest, sync behavioral memory                |
  |                                                                          |
  |  ITERATION START                                                         |
  |  +--------------------------------------------------------------------+  |
  |  |  7.1  HYPERAGENT DECIDES ACTION                                    |  |
  |  |  Agent: hyperagent (PERSISTENT, resumed via SendMessage)           |  |
  |  |                                                                    |  |
  |  |  Reads: archive stats, analysis insights, operator stats,          |  |
  |  |         dead-end catalog, behavioral memory                        |  |
  |  |                                                                    |  |
  |  |  Chooses ONE action:                                               |  |
  |  |    a. HP tuning      → delegates to tuning-agent                   |  |
  |  |    b. LLM code patch → modifies code directly (select parent,      |  |
  |  |                        create branch, edit code, validate)         |  |
  |  |    c. ShinkaEvolve   → dispatches evolve skill for fine-grained    |  |
  |  |                        mutations on selected parent branch         |  |
  |  |    d. Research       → dispatches research + implement agents      |  |
  |  |                        (from selected parent, not baseline)        |  |
  |  |    e. Meta-improve   → modifies skill instructions (max 3/session) |  |
  |  +--------------------------------------------------------------------+  |
  |                    |                                                     |
  |         +----------+----------+----------+----------+                    |
  |         |          |          |          |          |                    |
  |      hp_tune   llm_patch  shinka    research  meta_improve              |
  |         |          |      _evolve      |          |                     |
  |         v          v          v        v          v                     |
  |  +--------------------------------------------------------------------+  |
  |  |  7.2  EXECUTE ACTION                                               |  |
  |  |                                                                    |  |
  |  |  hp_tune:                                                          |  |
  |  |    tuning-agent proposes configs → experiment-agents run parallel   |  |
  |  |    monitor-agent watches for divergence (concurrent)               |  |
  |  |                                                                    |  |
  |  |  llm_patch / shinka_evolve / research_implement:                   |  |
  |  |    1. hyperagent-select → pick parent from archive                 |  |
  |  |    2. hyperagent-generate → create code variant                    |  |
  |  |       (ShinkaEvolve: evolve skill handles convert→run→inspect)     |  |
  |  |    3. hyperagent-eval → staged eval (10% budget, adaptive          |  |
  |  |       threshold). If FAIL → archive as filtered, skip full.        |  |
  |  |    4. If PASS → HP-tune (1-2 iters) + full experiment              |  |
  |  |                                                                    |  |
  |  |  meta_improve:                                                     |  |
  |  |    hyperagent-generate (meta_improvement_mode: true)               |  |
  |  |    → reads skill files + archive + operator stats                  |  |
  |  |    → writes patched skills to experiments/meta-patches/            |  |
  |  |    → writes meta-changelog.json (skill, change, reason, impact)   |  |
  |  |    → Step 5: IMMEDIATELY loads patches into subsequent dispatches  |  |
  |  |       "META-PATCHES ACTIVE: Read patched version instead"          |  |
  |  |    → tuning/analysis/research agents use improved instructions     |  |
  |  |       for ALL remaining iterations in this session                 |  |
  |  +--------------------------------------------------------------------+  |
  |                    |                                                     |
  |                    v                                                     |
  |  +--------------------------------------------------------------------+  |
  |  |  7.3  ARCHIVE RESULTS                                              |  |
  |  |  hyperagent-archive → update code-archive.jsonl                    |  |
  |  |    - Track genid, parent, lineage, fitness, mutation operator      |  |
  |  |    - Log to behavioral memory + research agenda                    |  |
  |  |    - Update operator_stats in hyperagent_state                     |  |
  |  +--------------------------------------------------------------------+  |
  |                    |                                                     |
  |                    v                                                     |
  |  +--------------------------------------------------------------------+  |
  |  |  7.4  ANALYZE                                                      |  |
  |  |  Agent: analysis-agent --> ml-optimizer:analyze skill              |  |
  |  |                                                                    |  |
  |  |  Decision tree:                                                    |  |
  |  |    "continue"         → resume hyperagent for next iteration       |  |
  |  |    "code_evolution"   → resume hyperagent (code mutation next)     |  |
  |  |    "hp_expand" etc    → resume hyperagent (HP tuning next)         |  |
  |  |    "stop"             → hyperagent tries other operators first       |  |
  |  |    "method_stacking"  → Phase 8 (merge methods, resolve interference)|  |
  |  |  If meta_improvement_recommended: true                             |  |
  |  |    → hyperagent may choose meta_improve next iteration             |  |
  |  |                                                                    |  |
  |  |  Analysis ADVISES direction, hyperagent DECIDES specific action.   |  |
  |  +--------------------------------------------------------------------+  |
  |         |                                                                |
  |         +-- Loop back to 7.1 HYPERAGENT DECIDES -->                       |
  |                                                                          |
  |  +--------------------------------------------------------------------+  |
  |  |  7.5  METHOD STACKING (when analysis recommends)                  |  |
  |  |  Triggered by: analyze returns pivot_type: "method_stacking"      |  |
  |  |  (multiple improved methods from different papers/code changes)    |  |
  |  |  Requires: git branch strategy                                    |  |
  |  |                                                                    |  |
  |  |  The hyperagent merges best methods sequentially:                  |  |
  +============================ END LOOP ====================================+

                    |
      (target achieved or user manually stops)

  PHASE 8: METHOD STACKING (in loop with Phase 7)
  =================================================
  Phase 7 ↔ Phase 8 loop. Analysis advises stacking, hyperagent decides.
  No fixed method count. After stacking → back to Phase 7 on stacked code.
  Agent: hyperagent drives stacking decisions
  Requires: git branch strategy (skipped for file_backup projects)

    +--------------------------------------------------------------+
    |  1. Rank methods by improvement (descending) using           |
    |     rank_methods_for_stacking() from result_analyzer.py      |
    |                                                              |
    |  2. Initialize: best method branch -> ml-opt/stack-1         |
    |                                                              |
    |  3. For each remaining method (in rank order):               |
    |     a. Create ml-opt/stack-<N> from <stack_base_branch>      |
    |        (may be an evolved branch from prior step)            |
    |     b. Merge next method; conflicts -> implement-agent       |
    |     c. Run experiment                                        |
    |     d. Dispatch analysis agent on stacked result:            |
    |        - Compare stacked gain vs best individual             |
    |        - If interference detected:                           |
    |          1. tuning-agent → evolve HPs                        |
    |          2. implement-agent → evolve (ShinkaEvolve)          |
    |          3. tuning-agent → training HPs for evolved          |
    |          4. experiment-agent → run on evolved code           |
    |          5. re-analyze → loop until improved or stop         |
    |        - Else: proceed to HP-tune                            |
    |     e. HP-tune on (potentially evolved) code                 |
    |     f. If degraded: skip, re-branch from last success        |
    |                                                              |
    |  4. Save stacking state (+ evolved_methods) to               |
    |     pipeline-state.json (resumable)                          |
    +--------------------------------------------------------------+

  Reads: results/exp-*.json, implementation-manifest.json, baseline.json
  Writes: results/exp-*.json (stacked_default_hp / stacked_tuned_hp)
          Git branches: ml-opt/stack-<N>

                    |
      (stacking complete → return to Phase 7 on stacked code)
      (target achieved or user stops → Phase 9)
                    v

  Phase 7 ↔ Phase 8 loop:
    Analysis advises "method_stacking" → Phase 8
    After stacking → back to Phase 7 on stacked code
    Meta-improvement inside Phase 7 (one of 5 actions)
    Loop until goal or user stops

  PHASE 9b: META-PATCH PROMOTION (if meta-improvements were made)
  ================================================================
  Agent: analysis-agent (meta_patches scope) + orchestrator

    1. analysis-agent evaluates each meta-patch:
       - Did experiments after the patch show improvement?
       - Is the modification generalizable?
    2. Present to user: "Promote N strategy improvements to plugin?"
    3. If approved → commit patched skills to plugin's current branch
       (immediately available next session, no merge needed)
    4. Log to behavioral memory + claude-mem for cross-session recall

  OPTIONAL: END-OF-SESSION REVIEW
  ================================
  Agent: analysis-agent --> ml-optimizer:analyze skill (review mode)

    - Self-improvement analysis
    - What worked, what didn't
    - Suggestions for future sessions

  Writes: experiments/reports/session-review.md

  First dispatch:    orchestrator --Agent(subagent_type="ml-optimizer:<name>-agent")--> agent
                     → save agentId to agent_registry["<name>"]
  Resume dispatch:   orchestrator --SendMessage(to: agentId, CONTEXT FROM OTHER AGENTS)--> agent
                     → if fails: fall back to fresh Agent(), update registry
  Agent preloads:    agent --skills: [ml-optimizer:<skill>]--> skill instructions
  User interaction:  [User]  <--->  [Orchestrator]
  Conditional:       (condition) ---> branch
  External skill:    context7, claude-mem, feature-dev, superpowers, alphaxiv
  MCP servers:       alphaxiv (paper search/analysis), claude-mem (cross-session memory)
  Data flow:         Reads: <file>  |  Writes: <file>

  Persistent agents: hyperagent, research, implement, tuning, analysis, monitor
                     Resumed via SendMessage — accumulate context across pipeline
                     Hyperagent is the PRIMARY loop driver (decides strategy)
  Ephemeral agents:  prerequisites, baseline, experiment, report
                     Fresh spawn each time — single-use or parallel tasks
  Analytical agents (ultrathink): Extended reasoning, model: opus
  Procedural agents (sonnet): Direct execution, lower cost/latency
  Agent memory: All agents have memory: local → .claude/agent-memory-local/<name>/
  Agent registry: pipeline-state.json → agent_registry (session-scoped, cleared on new session)
  Hyperagent state: pipeline-state.json → hyperagent_state (enabled, archive_generation,
                    strategy_history, meta_improvement_count, operator_stats)
  Code archive: code-archive.jsonl (JSONL — genid, parent, lineage, fitness, mutation_type)
  Meta-patches: experiments/meta-patches/ (session-scoped skill modifications)
  Goal anchor: optimization-goals.json (Phase 0, read by all agents)
  Behavioral memory: learned-behaviors.json (accumulated, project-scoped)

  Three-tier + stacking fields in exp-*.json:
    "method_tier":     "baseline" | "method_default_hp" | "method_tuned_hp"
                       | "stacked_default_hp" | "stacked_tuned_hp"
    "proposal_source": "paper" | "llm_knowledge" | null
    "code_branches":   ["ml-opt/a", "ml-opt/b"] (stacking only)
    "stacking_order":  integer position in stacking sequence
    "stack_base_exp":  exp_id of previous stack step
